# Split-движок скрининга (tgApi): полный контекст для ревизии

Документ самодостаточный — его можно вставить в чистый чат целиком. Задача нового обсуждения:
**найти проблемы, лишнюю сложность и способы упрощения/оптимизации**. Ниже — как оно работает
сегодня, со всеми вызовами, событиями, обновлениями состояния и ссылками на код.

Состояние на 2026-08-28. Ветки с незакоммиченной работой: `tgApi/feat/screening-salary-parser`,
`prompts/feat/screening-split-prompts`, `ai-agents/feat/screening-split-qa`.

> **ВАЖНО, читать первым.** Три копии движка **разошлись**: харнесс и промпт ушли вперёд относительно
> tgApi. Подробности — §9. Любая правка должна начинаться со сведения копий, иначе тесты гейтят не то,
> что в проде.

## 1. Что это такое

Чат-скрининг кандидатов. Вместо одного монолитного промпта — три участника:

| роль | что видит | что возвращает | где |
|---|---|---|---|
| **Аналитик** (LLM, gpt-4.1, `temperature 0`) | контекст вакансии (с вилкой), STATE, новое сообщение | строгий JSON `Decision` (7 полей) | `prompts/screening_analyzer` v2 |
| **Интервьюер** (LLM, gpt-4.1-mini) | только персона и имена — о вакансии НЕ знает | одно сообщение кандидату | `prompts/screening_interviewer` v2 |
| **Код-оркестратор** | всё | текст кандидату + флаг завершения | `tgApi/app/common/screening/ScreeningSplitEngine.py` |

Разделение по принципу least-privilege: Интервьюер не может слить вилку, потому что её не видит.
Аналитик не пишет кандидату, потому что его текст никуда не идёт напрямую. Завершение диалога —
всегда за кодом.

### Три копии одного движка

| канал | репозиторий | движок | промпты |
|---|---|---|---|
| прод, telegram | `tgApi` | `app/common/screening/ScreeningSplitEngine.py` | `screening_analyzer` / `screening_interviewer` |
| прод, hh | `eggplant-api` | `app/assistants/screening/engine.py` | `screening_analyzer_hh` / `screening_interviewer_hh` |
| QA-стенд | `ai-agents` | `src/qa_harness/domain/screening_split/engine.py` | те же, что у tg |

Промпты живут в отдельном репозитории `prompts`, ставятся в прод как пакет из GHCR-образа
`ghcr.io/podbor/prompts:latest` (пина версии нет — подхватывается при сборке образа).
Боевая версия компонента задаётся `prompts/<component>/pointer.yaml`.

## 2. Точка входа и цепочка вызовов (tgApi)

```
Telegram-драйвер получил сообщение
  └─ app/telegram/handlers/UnifiedReplyHandler.py:247  _screening_assistant_message_generator
       ищет conversation_id в Mongo (коллекция assistant_threads по sender+recipient)
     └─ app/common/messages.py:197  screening_message_generator
          └─ ScreeningAssistant(database)                       app/common/screening/ScreeningAssistant.py:52
               ├─ create_thread(...)   — только если conversation_id ещё нет
               └─ add_message_and_run(conversation_id, message)
                    └─ если store.engine_of(cid) == "split":   ScreeningAssistant.py:72
                         ScreeningSplitEngine.add_message_and_run(...)
                       иначе → ConversationResult(None, end=True)   # до-split диалоги штатно закрываем
     └─ вернулся (answer, end_conversation)
  └─ UnifiedReplyHandler:180  _send_message(driver, answer)   — единственная точка отправки
  └─ UnifiedReplyHandler:186  если conversation_ended → закрываем чат
```

Дополнительно `screening_message_generator` собирает Report для внутреннего канала (аккаунт, контакт,
компания, текст сообщения) — на логику не влияет.

**Важно про архитектуру:** движок **событийный** (пришло сообщение → ход), в отличие от eggplant, где
ход запускается периодическим тиком и есть outbox (`pending_text`). Поэтому здесь нет согласования
отправки: при сбое отправки ход просто теряется.

### `create_thread` — что происходит на старте

`ScreeningSplitEngine.create_thread` (`ScreeningSplitEngine.py:155`):

1. `ctx.candidate_source(candidate_accounts)` → метка источника контакта (hh/LinkedIn/…);
2. `ctx.build_context(...)` → **полный** лейблованный контекст с вилкой — только для Аналитика;
3. `ctx.build_interviewer_seed(...)` → сид Интервьюера, только имена;
4. `client.conversations.create(items=[{role: assistant, content: seed}])` → создаётся
   OpenAI-conversation, её id становится `conversation_id` диалога;
5. `state_model.init_state(work_format, questions)` → стартовый STATE;
6. `store.create(...)` → запись в Mongo (`screening_state`) с `state`, `context`, `location`,
   `contact_source`, `salary_band` и `engine: "split"`.

## 3. Один ход: `add_message_and_run` по шагам

Файл: `tgApi/app/common/screening/ScreeningSplitEngine.py` (378 строк).

```
0.  store.load(cid)                      нет записи → REPLY_FALLBACK, не завершаем
                                         doc["finished"] → (None, end=True), молчим
1.  progress_before = progress_signature(state)
2.  analyzer.run(context, state, message) → Decision            ← ВЫЗОВ LLM #1
       сбой (AssistantError) → REPLY_FALLBACK, не завершаем
3.  ЗАРПЛАТА, часть 1: разбор claim
       claim        = salary.read_claim(decision)
       claim_status = salary.claim_status(claim, message)        absent | unusable | actionable
       если actionable: salary_value = salary.normalize(claim)
                        None → claim_status = UNUSABLE          (порядок важен, см. §5)
4.  apply_updates(state, _gate_salary_update(updates, claim_status))
       БЕЗ event — инкремент отложен до конца всех вызовов LLM (см. §6)
5.  ПЕРЕРЕШИВАНИЕ (если claim непригоден И решение исходило из «деньги закрыты»)
       analyzer.run(context, new_state, message, note=...)      ← ВЫЗОВ LLM #2 (условный)
       event второго решения игнорируется, updates гейтятся тем же статусом
6.  ЗАРПЛАТА, часть 2: вердикт по вилке
       compare_with_band(value, band_min, band_max) → ko | fits
       ko   + вердикт вправе перебить → KO_SALARY (_forced = True)
       fits → salary = closed; если решение было денежным завершением → снимаем его
7.  ИНКРЕМЕНТ event (первого решения)   apply_updates(new_state, [], _event)
8.  АУДИТ: store.log_salary_claim(cid, entry)   если claim_status != absent
9.  ПОРОГИ СОБЫТИЙ (_EVENT_STOP по _event)      → форс STOP_* (_forced = True)
10. REASK-CAP по decision.asking                → форс STOP_* / refused + перерешивание
       перерешённый ход (шаг 5) кап НЕ жжёт
       исчерпан доп-вопрос → refused + analyzer.run(...)        ← ВЫЗОВ LLM #3 (условный)
11. NO_PROGRESS-CAP  (сигнатура не изменилась 4 хода подряд)    → FINISH | STOP_PERSISTENT
12. РЕНДЕР
       next_action == script → scripts.render_script(key, city, contact_source)
                               end = scripts.is_terminal(key)   (терминально всё, кроме REPLY_*)
                               неизвестный ключ → REPLY_FALLBACK, end = False
       next_action == ask    → interviewer.run(cid, instruction, message)  ← ВЫЗОВ LLM #4
                               new_state["last_asked"]  = instruction
                               new_state["last_asking"] = decision["asking"]
13. store.save_state(cid, new_state, finished=end)
14. return ConversationResult(text or None, end)
```

**Сколько вызовов LLM за ход:** Аналитик 1 (обычно), 2 (перерешивание по зарплате ИЛИ исчерпанный
доп-вопрос), максимум 2 — третьего быть не может, потому что перерешённый ход не проходит через
reask-cap. Плюс Интервьюер 0 или 1. Итого 1–3 вызова.

## 4. Контракт `Decision` — 7 полей

Схема: `prompts/prompts/screening_analyzer/v2/config.yaml`, `strict: true`,
`additionalProperties: false`, все поля в `required`.

| поле | значение |
|---|---|
| `next_action` | `ask` \| `script` |
| `script_key` | ключ скрипта при `script`, иначе `null` |
| `instruction` | директива Интервьюеру при `ask`, иначе `null`. Максимум 2 задаваемых вопроса |
| `updates` | `[{key, value}]` — что изменилось на этом ходе |
| `event` | `bot_check` \| `gibberish` \| `salary_info` \| `demand` \| `contact_source` \| `pause` \| `null` |
| `asking` | `salary` \| `format` \| `q1`/`q2`/… \| `null` — по нему код считает переспросы |
| `salary_claim` | объект из 9 полей либо `null` — что кандидат сказал про деньги (см. §5) |

Валидация — `ScreeningAnalyzerAssistant._parse_and_validate` (`ScreeningAnalyzerAssistant.py:71`):
JSON → объект → наличие 6 обязательных полей (**`salary_claim` в список НЕ входит**: негодное
зарплатное поле не должно стоить трёх перегенераций хода, и код обязан работать со старой версией
промпта) → `next_action` в перечислении → при `script` ключ известен реестру (`scripts.is_known`) →
при `ask` непустая `instruction` → `updates` список из dict с `key`/`value` → `event` в `COUNTER_KEYS`.
Невалидно → до 3 попыток с приклеенной служебной строкой `[Система: предыдущий ответ невалиден — …]`.
Исчерпаны → `AssistantError` → `REPLY_FALLBACK`.

### `updates` — что кладётся в STATE

`{key: salary, value: closed}` · `{key: format_check, value: closed}` ·
`{key: candidate_city, value: <город>}` · `{key: q2, value: closed}`.
Мёрж **монотонный** (`screening_state.apply_updates`): `closed`/`refused` не откатываются,
`reasked` инкрементит `reask_count`, неизвестные ключи игнорируются.

## 5. Зарплата: контракт `salary_claim`

Граница проведена по линии **«понимание ↔ вычисление»**: Аналитик слышит, код считает.
Модули: `app/common/screening/salary.py` (189 строк, регулярок по тексту ноль) и
`salary_rules.py` (30 строк, только данные).

### Поля claim

`subject` (`own_expectation` / `own_current` / `third_party`) · `form` (`exact` / `range` /
`at_least` / `at_most` / `relative_only` / `not_stated`) · `amount_min`, `amount_max` — **РОВНО как
названо, без домножения** · `scale` (`none_stated` / `unit` / `thousand` / `million`) ·
`currency` (`RUB` / `USD` / `EUR` / `KZT` / `other`) · `period` (`month` / `hour` / `day` / `week` /
`year`) · `tax` (`net` / `gross` / `unspecified`) · `quote` — дословный фрагмент реплики.

Два свойства, на которых держится конструкция:
- **модель не умножает** — масштаб применяет код, поэтому соглашения (голое число = тысячи, курсы,
  нормо-часы, НДФЛ) меняются без релиза промпта;
- **все словари — закрытые `enum`** — поэтому неоднозначность, которую код может обнаружить, модель
  видит в момент, когда пишет `instruction`; коды причин из кода в промпт не перекладываются.

### Четыре гейта годности (`salary.claim_status`)

1. `quote` найден в реплике кандидата и содержит цифру (или числительное словом) — защита от
   выдуманной суммы, без судьи и без токенов;
2. `subject == own_expectation` — чужая и текущая суммы пункт не закрывают;
3. форма несёт сумму и `currency` в справочнике;
4. claim не противоречит себе — обе границы пустые либо `min > max`.

Не прошёл → `unusable`. Это **не ошибка**: уточняющий вопрос Аналитик задал в том же ходе.

### Арифметика (`salary.normalize`) и вердикт

Порядок: масштаб (`none_stated` и число < 1000 → ×1000) → курс → период (норма 160 ч/мес) →
`gross` → net по прогрессивной шкале НДФЛ → проверка на противоречие.

`compare_with_band`: **отказ только если даже НИЖНЯЯ граница ожиданий выше нашего максимума**
(«250-400» при вилке до 280 — не отказ). Полосы терпимости нет. Сумма ниже минимума вилки —
никогда не отказ. `band_min` в функцию передаётся, но не используется — намеренно, чтобы правило
было видно на вызове.

Данные пересчёта — `salary_rules.py` с `SALARY_RULES_VERSION`. Не env и не конфиг: курсы обязаны быть
одинаковы во всех портах, а версия имеет смысл только если меняется вместе с кодом (на неё ссылается
аудит-запись).

### Вилка: откуда

`doc["salary_band"]` (кладётся в `create_thread`). У диалогов, начатых до правки, ключа нет — движок
достаёт границы регуляркой `_BAND_RE` из строки контекста, поэтому миграции не потребовалось.

### Аудит-запись

`store.log_salary_claim` → `$push` в массив `salary_claims` документа диалога:
claim как пришёл · `status` · `normalized` · `applied` · `rules_version` · `verdict` ·
`effect` (`ko_forced` / `ko_overridden_by_analyzer` / `closed` / `closed_money_stop_released`) ·
`rewind`. Движок её **не читает**: в `state` числа нет вообще (только `pending|closed`), а у
отсеянного кандидата сводки для рекрутера не создаётся — без этой записи отказ по деньгам
невоспроизводим.

## 6. Счётчики, пороги и приоритеты решений

### Механизмы завершения — их пять, и они перекрываются

| механизм | что считает | инкремент | сброс | эффект на пороге |
|---|---|---|---|---|
| `gibberish` | бессвязные реплики | `event` от Аналитика | нет | `STOP_GIBBERISH_REPEAT` на 2-м |
| `bot_check` | «вы бот?» | `event` | нет | `STOP_BOT_REPEAT` на 2-м |
| `demand` | настойчивость кандидата | `event` | нет | `STOP_PERSISTENT` на 3-м |
| `contact_source` | требование раскрыть источник | `event` | нет | `STOP_PERSISTENT` на 3-м |
| `pause` | просьбы отложить | `event` | нет | `STOP_PAUSE` на 3-м |
| `salary_info` | требования НАШЕЙ вилки | `event` | нет | **порога в коде нет** — читает только промпт |
| reask-cap (`salary_reasks`, `format_reasks`, `q*.reask_count`) | повторные заходы на один незакрытый пункт | `asking == last_asking` и пункт `pending` | нет | зарплата → `STOP_SALARY_DEMAND`; формат → `STOP_PERSISTENT`; доп-вопрос → `refused` + перерешивание |
| `no_progress` | ходы без нового факта | сигнатура не изменилась | **да, в 0** | `FINISH` если всё собрано, иначе `STOP_PERSISTENT` |

`progress_signature` = (`salary`, `format_check`, есть ли город, статусы `q*`). `reask_count` в неё НЕ
входит. Пороги проверяются **до** инкремента, поэтому «порог 2» = срабатывание на 3-м повторе.

**Известное перекрытие:** reask-cap, `demand` и `no_progress` ловят одно и то же «диалог не двигается»
тремя разными признаками, и первые два срабатывают за 2–3 хода — из-за чего 4-й ход без прогресса
живьём почти недостижим. Разбирали, решили не менять: `no_progress` остаётся страховкой.
**Это первый кандидат на упрощение.**

### Инкремент `event` отложен до конца всех вызовов LLM

Счётчик описывает поведение кандидата **в этом сообщении**, значит каждый вызов Аналитика на ходе
обязан видеть его одинаковым. Иначе второй вызов читает «вы бот?» из этой же реплики как ПОВТОР
(в счётчике уже единица от текущего хода) и завершает диалог `STOP_BOT_REPEAT` кандидату, который
спросил один раз. Порог ниже проверяется по `_event` — событию **первого** решения, потому что именно
оно попало в счётчик.

### Кто выигрывает при конфликте

| ситуация | результат |
|---|---|
| claim годен + `ko` + решение `ask` | `KO_SALARY` |
| claim годен + `ko` + сработал событийный порог | `KO_SALARY` (зарплатный блок стоит ВЫШЕ порогов) |
| claim годен + `ko` + модель дала `KO_SALARY` / `STOP_SALARY_DEMAND` / `STOP_NOT_INTERESTED` / `FINISH` | `KO_SALARY` от кода |
| claim годен + `fits` + модель дала денежное завершение | решение модели **снимается**, диалог продолжается |
| claim годен + `fits` + модель дала `FINISH` | `FINISH` остаётся |
| claim годен (любой вердикт) + модель дала НЕденежное терминальное (`STOP_ABUSE`, `STOP_POLITICS`, `KO_FORMAT_*`, …) | решение **модели** |
| claim `unusable` / `absent` | зарплатного форса нет |

Границы заданы двумя константами: `_MONEY_DECISIONS` (что снимает `fits`) и
`_KO_OVERRIDABLE = _MONEY_DECISIONS | {FINISH}` (что перебивает `ko`). Наборы разные намеренно.

### Перерешивание хода

Триггер: claim `unusable` **и** `_assumes_salary_closed(decision, state)` — модель сама поставила
`salary: closed`, вернула `FINISH`, либо `asking` уехал на следующий приоритет. `asking: null` НЕ
признак: отвечать на вопрос кандидата, не двигая приоритеты, законно.

Второму вызову передаётся служебная строка `_SALARY_REWIND_NOTE`. Без неё вход тождественный (state не
менялся, потому что отклонённое `salary: closed` в него не попало), и при `temperature 0` модель
повторяет то же решение — перерешивание становится no-op. Это проверено прогоном.

Перерешённый ход **не жжёт reask-cap**: вопрос задан из-за нашей ошибки, а не уклонения кандидата.

## 7. Скрипты и завершение

Реестр — `app/common/screening/screening_scripts.py` (131 строка). Терминальность **по префиксу**:
всё, кроме `REPLY_*`, завершает диалог (`is_terminal`).

- `KO_*` — отсев по объективным критериям вакансии: `KO_SALARY`, `KO_FORMAT_OFFICE`,
  `KO_FORMAT_HYBRID`, `KO_FORMAT_NOCITY`, `KO_GEO`, `STOP_ABROAD` (рудимент, подлежит удалению);
- `STOP_*` — ситуативное завершение со стороны кандидата (политика, оскорбления, флирт, мошенничество,
  уже трудоустроен, не интересно, критика, декрет и т.п.);
- `FINISH` — успех;
- `REPLY_CONTACT_SOURCE`, `REPLY_CONTACT_SOURCE_EMPTY`, `REPLY_FALLBACK` — нетерминальные.

Подстановки: `{city}` (локация вакансии), `{contact_source}`. При пустом `contact_source` ключ
`REPLY_CONTACT_SOURCE` подменяется на `_EMPTY`-вариант внутри `render_script`.

**Известный дефект:** `STOP_POLITICS` имеет **пустой текст** — кандидат не получает ничего, диалог
выглядит оборванным. В eggplant это исправлено, здесь нет.

### Кто какие ключи ставит (после правки Б5)

- **только модель:** `KO_FORMAT_*`, `KO_GEO`, ситуативные `STOP_*`, `FINISH`, `REPLY_CONTACT_SOURCE`;
- **только код:** `KO_SALARY`, `STOP_SALARY_DEMAND`, `STOP_PERSISTENT`, `STOP_GIBBERISH_REPEAT`,
  `STOP_BOT_REPEAT`, `STOP_PAUSE`, `REPLY_FALLBACK` + `FINISH` через `no_progress`-кап.

Имена код-форсимых ключей из промпта **удалены**: каждый упоминается ровно один раз, в прямом запрете
«не выставляй никогда». Пороги совпадали и до правки, поэтому поведение не изменилось — изменилось
то, кто ставит ключ. `FINISH` оставлен у модели: код форсит его только как страховку, и без модели
успешный скрининг завершался бы лишь через 4 хода без прогресса.

## 8. Промпты

### `screening_analyzer` v2 — 40 315 символов (~356 строк)

`prompts/prompts/screening_analyzer/v2/system.md`. Структура:

1. **РОЛЬ** — «кандидат тебя не видит», решай только по STATE и новому сообщению;
2. **ВХОДНЫЕ ДАННЫЕ** — три блока: контекст вакансии (лейблы, вилка «НЕ РАСКРЫВАТЬ»), STATE (описание
   каждого поля + список служебных, которые надо игнорировать), новое сообщение;
3. **ВЫХОД** — таблица 7 полей, три примера JSON, значения `updates`, кто ставит какие ключи;
4. **ФАКТЫ И ФОРМАТ `instruction`** — самый нагруженный блок: Интервьюер о вакансии не знает, поэтому
   факт надо вложить в инструкцию дословно; «директива без значения запрещена»; инструкция — директива
   Интервьюеру, а не реплика кандидату; запрет пересказывать сказанное кандидатом; три обязательные
   части (что донести / о чём спросить / чего не раскрывать); ❌/✅-примеры;
5. **ПОРЯДОК РЕШЕНИЯ** — Шаг 0 язык (проверяется ДО всего), Шаг 1 триггеры, Шаг 2 основной алгоритм;
6. **ТРИГГЕРЫ** — таблица приоритета (politics → abuse → flirt → grief → money → foreign_lang →
   fraud_check → already_employed → not_interested → no_experience → criticism → gibberish →
   task_request → answer_aid → salary_info → contact_source → company_info → scheduling → pause),
   таблица терминальных с маркерами, таблица нетерминальных, раздел «разруливание близких триггеров»;
7. **KNOCKOUT-КРИТЕРИИ** — §1 ЗАРПЛАТА (контракт `salary_claim`, ~60 строк), §2 формат/локация
   (радиусы: Москва +100 км, прочие +50 км; сценарии A/B/C), §3 `KO_GEO`;
8. **СКРЫТОСТЬ КОМПАНИИ**, **НЕСКОЛЬКО ВОПРОСОВ В ОДНОМ СООБЩЕНИИ**;
9. **ОСНОВНОЙ АЛГОРИТМ** — старт, приоритеты (зарплата → формат → questions → финиш), обработка
   ответа, «кандидат не отвечает по сути», «давление кандидата», «нет данных», финиш;
10. **НАПОМИНАНИЕ ПО ВЫХОДУ**.

Параметры (`config.yaml`): `gpt-4.1-2025-04-14`, `temperature 0`, `top_p 1.0`,
`max_output_tokens 2048`, `store: true`, `text_format: json_schema` (`strict: true`).

### `screening_interviewer` v2 — 8 307 символов

Знает только персону и имена. Получает `instruction` + сообщение кандидата, отдаёт одно сообщение.
Внутри есть секция «РАНТАЙМ-САНИТАЙЗЕР (перед отправкой)» — модель просят делать работу кода
(разбить по предложениям, убрать дубли, убрать прощальные формулы при наличии вопроса, вырезать `END`).
**Это кандидат на вынос в код** (задача Б4).

### Как вызываются

`app/common/llm_client.py`:
- Аналитик — **stateless**: `conversation_id=None`, вход собирается целиком каждый ход;
- Интервьюер — **stateful**: `conversation=<id>`, `instructions=system_text`, во `input` только ход.
  Поэтому `store` у него остаётся продовым: при `store=false` новые input/output не дописываются
  в conversation и история ходов теряется.

## 9. РАСХОЖДЕНИЕ КОПИЙ — читать до любой правки

### tgApi vs харнесс

Харнесс (`ai-agents/src/qa_harness/domain/screening_split/engine.py`) содержит **второй случай
перерешивания**, которого в tgApi НЕТ:

> код принял сумму и закрыл пункт, а решение всё ещё переспрашивает про деньги
> (`next_action == ask` и `asking == salary`) → второй вызов Аналитика **без** служебной строки:
> состояние реально изменилось (`pending → closed`), и второй вызов увидит это сам.
> `effect = "closed_reask_dropped"`. Заведено по прогону 28.08, сценарий 45.

Причина появления: промпт изменили так, что модель **больше никогда** не ставит `salary: closed`
(см. ниже) — значит на ходе, где кандидат назвал сумму, она не знает, что пункт закроется, и может
переспросить. Без второго вызова кандидату уходит вопрос, на который он только что ответил.

### Промпт vs tgApi

В промпте теперь: **«`salary` в `updates` НЕ ставь никогда» — этот пункт закрывает КОД.**
Раньше было «ставь только вместе с годным claim».

Следствия для tgApi, которые надо проверить:
- `_gate_salary_update` теряет работу (гейтить нечего) — но убирать его нельзя, пока промпт не в проде;
- первая ветка `_assumes_salary_closed` (updates содержит `salary: closed`) становится недостижимой;
- **появляется новый класс расхождения**, который tgApi не обрабатывает: код закрыл, модель
  переспрашивает. Именно его закрывает второй rewind в харнессе.

### Что это значит практически

Гейт харнесса (50 офлайн-проверок + сценарии) сейчас проверяет **не ту логику**, что в tgApi.
Первый шаг любой работы — решить, переносить ли второй rewind в tgApi, и свести копии.

### hh-контур

`screening_analyzer_hh` v2 на контракт **не переведён**: там полный 27-строчный зарплатный блок с
арифметикой и правила, ПРЯМО противоречащие принятым (диапазон по верхней границе, голое «260»
уточнять, gross с вилкой не сравнивать). `eggplant-api` кода контракта не имеет.
`pointer.yaml`: `screening_analyzer_hh` → v2, `screening_interviewer_hh` → **v1** (версии разъехались).

## 10. Тесты и как проверять

Тестов в tgApi **нет** (решение 27.08.2026: в репозитории нет ни тестов, ни правил покрытия).
Весь детерминированный гейт — в харнессе.

```bash
# гейт кода: 50 проверок, без сети и токенов. Провал валит прогон
python -m qa_harness.runners.screening_split --offline --sample 0

# живые сценарии, детерминированный вход (реплики дословно из фикстур)
python -m qa_harness.runners.screening_split --input-mode scripted --sample 0 --prompts-path ../prompts

# вариативный: реплики генерит LLM-кандидат, засеянный из рецепта
python -m qa_harness.runners.screening_split --input-mode generated --variants 2 --temperature 0.7 --sample 0 --prompts-path ../prompts

# структурный контракт qa_harness ⊥ app
lint-imports
```

Три слоя оценки с атрибуцией ошибки:
- **A (Аналитик)** — детерминированные инварианты `Decision`/state по трассе
  (`tests/fixtures/screening_split/scenario_checks.yaml`): `expect_script_key`, `expect_salary`,
  `expect_salary_status`, `expect_salary_effect`, `expect_asking`, `expect_event`, `expect_end`,
  `expect_instruction_lacks`, `expect_instruction_url_valued` и др. LLM-судьи нет;
- **B (Интервьюер)** — `leak_scan` (детерминированный: утечка вилки, выдуманный URL, эмодзи) +
  `InterviewerJudge` (LLM: верно ли передан СМЫСЛ инструкции этого хода);
- **C** — `ScenarioJudge` (LLM), только для сценариев без инварианта. Сейчас все 77 сценариев имеют
  инвариант, поэтому слой C не зовётся.

`--prompts-path ../prompts` **обязателен**: без него берётся установленный релиз из GHCR, где правок
контракта нет.

Последние прогоны (2026-08-27/28): scripted 19 зарплатных — 19/19; generated `--variants 2` на всех
77 — **145/154**, из 9 провалов ни один не связан с зарплатным контрактом (4 дрейф генератора,
1 пограничное распознавание, 3 дефекта промпта старше правки, 1 претензия судьи слоя B).

## 12. Что уже известно как проблема — стартовый список для ревизии

Не полный: это то, что нашли по ходу работы и сознательно оставили.

**Сложность и перекрытия**
1. **Пять механизмов завершения** (§6) ловят пересекающиеся ситуации; `no_progress` живьём почти
   недостижим. Кандидат на упрощение.
2. **`_forced`-флаг протаскивается через четыре блока** — порядок проверок стал неявной логикой.
3. **Промпт Аналитика 40 тыс. символов уходит в КАЖДЫЙ вызов** (Аналитик stateless). При 1–3 вызовах
   на ход это основная статья расхода: полный прогон 77 сценариев ≈ 2,5 млн input-токенов.
   Кандидат на оптимизацию (кэширование промпта? разделение на статическую/динамическую часть?).
4. **`_release_money_stop` и два перерешивания** — три разных способа «переиграть решение модели»
   в одном методе.
5. **Санитайзер в промпте Интервьюера** — модель просят делать механическую работу кода (Б4).

**Корректность**
6. **Копии разошлись** (§9) — главное.
7. **Пустой `STOP_POLITICS`** — кандидат не получает ничего.
8. **Ошибка модели в `scale`/`currency`/`period` ничем не ловится** и даёт ложный `KO_SALARY`:
   `million` вместо `thousand` — ×1000, `USD` вместо `RUB` — ×80, оба дают правдоподобное число.
   Потолок правдоподобия снят сознательно (он был абсолютным, а не относительным к вилке).
   Наблюдение из прогонов: модель **не всегда переносит число дословно** — «240000 рублей» приходило
   как `240 + thousand`, то есть механизм пересчёта в модели активен.
9. **Семантическая ошибка модели неотличима**: пометит ожидания как `own_current` — код спишет
   непригодность на кандидата.
10. **`expect_event` на перерешённых ходах** (харнесс): в трассу попадает второе решение, у которого
    `event` обычно `null`, хотя счётчик вырос по событию первого.
11. **P11: валюта вилки.** В tg вилка рублёвая по построению; в hh приходит из
    `hh_vacancy_data["salary"]["from"/"to"]`, а поле `currency` из того же объекта **не читается** —
    вилка в тенге сравнивается как рублёвая.
12. **Ложное завершение на вопрос о других вакансиях** — прогон 28.08, сценарии 66/v1,v2: «это не
    LLM-направление, есть что-то подходящее?» → `STOP_NOT_INTERESTED`. Класс инцидента 17.08.
13. **`fraud_check` проигрывает `contact_source`** — прогон 28.08, сценарий 7/v1: «откуда контакт и
    почему не с корпоративной почты» → `REPLY_CONTACT_SOURCE`, хотя правило разруливания предписывает
    `STOP_FRAUD_CHECK` при обоих признаках в одном сообщении.
14. **Три копии `salary_rules.py`** — курсы и НДФЛ в каждом порте отдельно, защита только сверкой
    глазами (Б2).
15. **`STOP_ABROAD`** — рудимент в реестре, промпт его больше не эмитит.
