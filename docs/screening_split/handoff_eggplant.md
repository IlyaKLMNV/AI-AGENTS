# Порт policy-ядра в eggplant-api — контекст для новой сессии

Состояние на 31.08.2026. Документ отвечает на «что где лежит» перед началом hh-порта: где эталон,
куда переносим, чем каналы отличаются и в каком порядке работать. Механику самого ядра не
пересказывает — она в [mechanics_policy.html](mechanics_policy.html) и
[handoff_two_engines.md](handoff_two_engines.md).

## 1. Где мы сейчас

Ветки, коммиты и состояние всех четырёх репозиториев — в [../repos.md](../repos.md) (единственный
источник: держать это в двух файлах уже приводило к расхождению). Здесь только то, что относится
именно к порту:

- **исходник переноса — `domain/screening_split_hh/policy/` в харнессе**, не tg-ядро: оно уже
  канальное (мультиформат, `field_work`, ключи отсева hh);
- **эталон обвязки — ветка PR в `tgApi`**: состав ниже, §2;
- **ветку под порт заводить от свежего `master` `eggplant-api`**, не от текущей — там идёт чужая
  работа (`fix/screening-session-rollback`). Untracked-файлы репозитория (`TODO_salary_reask_cap.md`,

Состав PR (все пути от `tgApi/app/common/screening/`):

| что | файлы |
|---|---|
| ядро | `policy/`: `core.py` (436) · `rules.py` (152) · `guards.py` (169) · `observation.py` (150) · `reasons.py` (135) · `migration.py` (94) · `context.py` (66) · `gates.py` (56) · `budgets.py` (47) · `__init__.py` |
| зарплата | `salary.py` (156) · `salary_rules.py` (22) |

| оркестратор | `ScreeningSplitEngine.py` — 378 → 139 строк |

Решения, принятые уже после переноса ядра (в eggplant поедут вместе с ним):

- **`schema: 2` пишется при создании диалога**, поэтому ленивая миграция (`policy/migration.py`)
  трогает только документы, созданные до выката. Удалять её можно, когда
  `db.screening_state.count_documents({"schema": {"$ne": 2}, "finished": false})` вернёт ноль;
- `init_state()` кладёт `last_sent`, из дефолтов миграции убран `closed_reason` (никем не читался);
- восстановлен `REPLY_CONTACT_SOURCE_EMPTY` — при пустом источнике контакта новый реестр иначе
  подставлял дефолт в шаблон и выдавал «Коллеги указали источник контакта **как из базы кандидатов**»;
- **в файлах PR нет ни одного комментария и докстринга** — снято по требованию владельца репо
  (осталась только прагма `# noqa: BLE001`). Для `eggplant-api` это правило **не действует
  автоматически**: там свой `CLAUDE.md` и своя плотность комментариев — решать отдельно.

Готовое описание PR (Mongo-миграция, изменения поведения, что проверено) — в истории сессии; при
необходимости пересобирается из этого файла и `handoff_two_engines.md`.

## 3. Куда переносим — карта `eggplant-api`

Скрининг: `app/assistants/screening/` — 549 строк против ~1300 у нового tg-ядра.

| файл | строк | роль |
|---|---|---|
| `engine.py` | 174 | оркестратор, **async**. `run_turn(dialogue, message) -> (text, ended)`; мутирует запись, но НЕ коммитит |
| `assistants.py` | 129 | `ScreeningAnalyzerAssistant` (валидатор `Decision` на 6 полей) + `ScreeningInterviewer` (**stateful**, через `conversation_id`) |
| `state.py` | 113 | `init_state`/`apply_updates`/`progress_signature`/`is_complete`/`find_question` |
| `scripts.py` | 81 | реестр текстов + `is_known`/`is_terminal`/`render_script`/`fallback_text` |
| `context.py` | 52 | `build_context` (вилка строкой внутри), `build_interviewer_seed`, `build_greeting` |

Обвязка вокруг:

- **вызов движка** — `app/assistants/service.py`: `create_screening_conversation` (создаёт
  `ScreeningDialogue` + conversation, `init_state(allowed_formats, screening_questions)`),
  `generate_screening_message` → `run_turn`, плюс **двухфазная отправка**:
  `get_pending_screening_message` / `confirm_screening_send`;
- **хранилище** — Postgres, `app/assistants/models.py::ScreeningDialogue` (`screening_dialogues`):
  ключ `openai_conversation_id`, `state` — **JSONB**, плюс колонки `context`, `location`, `greeting`,
  `pending_text` (outbox), `finished`. Запись — `app/assistants/repository.py::save_state`;
- **промпты** — не хардкод, а конфиг: `config.SCREENING_ANALYZER_PROMPT_NAME` /
  `SCREENING_INTERVIEWER_PROMPT_NAME`;
- **миграции — Alembic** (`app/migrations/versions/`, конфиг `alembic.ini`). Любое новое поле уровня
  колонки требует ревизии — в отличие от Mongo, где схема поменялась молча. Поля внутри `state`
  (JSONB) миграции не требуют;
- **тесты есть и они гейт**: `app/tests/assistants/test_screening_engine.py` (367),
  `test_screening_state.py` (146), `test_screening.py` (96), `test_screening_scripts.py` (53).
  `test_screening_engine.py` ассертит ровно ту механику, которую порт отменяет (`TestCounterCaps`,
  `TestReaskCaps`, перерешивание хода) — при переносе ядра переписывается целиком;
- **конвенции — их**: `eggplant-api/CLAUDE.md` (архитектурный курс «тонкий прокси над HH»),
  `TASKS.md`, `TECH_DEBT.md`. Коммиты `PO-#### англ. суть (#PR)`, pytest гоняется **из их репозитория**,
  не из штаба.

## 4. Чем hh отличается от tg — что нельзя потерять при порте

| | tgApi (эталон) | eggplant-api |
|---|---|---|
| исполнение | синхронное | **async** во всём тракте (`run_turn`, ассистенты) |
| хранилище | Mongo, документ схемы-по-факту | Postgres + JSONB, колонки через Alembic |
| отправка | сразу текстом из хода | **outbox**: `pending_text` → `confirm_screening_send` |
| приветствие | нет | `greeting` приклеивается к первому сообщению, флаг `state.greeted` |
| повестка | зарплата, формат, доп-вопросы | **плюс `field_work_check`** и `allowed_formats` в state (мультиформат: `REMOTE` среди допустимых снимает проверку присутственного) |
| ключи отказа | `KO_FORMAT_OFFICE`/`HYBRID`/`NOCITY`, `KO_GEO` | `KO_LOCATION`, **`KO_LOCATION_GEO`**, `KO_FORMAT` |
| источник контакта | событие `contact_source` + скрипт | **нет ни события, ни скрипта** (и в `EVENT_STOP`, и в `COUNTER_KEYS` его нет) |
| лимит переспросов | по пунктам раздельно, порог 3 по новой семантике | `REASK_CAP = 2`, **общий** для salary/format/field_work/вопросов, старая семантика «сверяем до инкремента» |
| зарплата | `salary_claim` → гейты → сравнение с типизированной вилкой | **модуля нет вовсе**: вилка живёт строкой в `context`, решение целиком за моделью, `currency` из HH не читается (вилка в тенге сравнивается как рублёвая) |
| промпт Аналитика | `screening_analyzer` **v3** (контракт `Observation`), уже в выпущенном пакете | `screening_analyzer_hh` **v3** написан, но не закоммичен и не выпущен |
| промпт Интервьюера | `screening_interviewer` v2 | `screening_interviewer_hh` v1 |

`screening_analyzer_hh` v2 вдобавок содержит зарплатные правила, **прямо противоречащие** принятым
для tg (диапазон по верхней границе, уточнять голое «260», gross с вилкой не сравнивать) — переносим
не правки v2, а контракт `Observation`.

## 5. Порядок работ

Живой список с формулировками и приоритетом — [plan_cross_repo.md](plan_cross_repo.md), раздел
«hh-контур» (плюс **Б3** — кандидаты за границей). Здесь только последовательность самого порта; то,
что уже готово в харнессе, описано в §5.1–§5.4 и служит исходником.

1. **ядро в `eggplant-api`** — `policy/` + зарплатный модуль (его там нет вовсе), async-обвязка,
   гарды внутри движка (отдельной точки санитайзера в `HHClient.send_message` заводить не надо);
2. **хранилище** — решить, где живёт типизированная вилка `{min, max, currency}`: колонка в
   `screening_dialogues` (Alembic-ревизия) или сборка на лету из данных вакансии HH. В tg это поле
   документа плюс ленивая миграция; в Postgres миграция обязательна и должна быть явной. Ядро читает
   вилку из одного места (`DecideContext`), поэтому решение локальное;
3. **`REASK_CAP`** — привести к 3 по новой семантике (Р3), иначе пороги каналов разъедутся;
4. **тесты** — переписать `test_screening_engine.py` под ядро; завести анти-луп кейсы
   (`counter_loops.yaml`-аналог), которых в hh нет вовсе.

### 5.1. Что в `screening_analyzer_hh/v3`

Контракт `Observation` тот же, что в tg (7 полей), с двумя канальными отличиями — остальное, включая
блок `salary_claim`, перенесено из `screening_analyzer/v3` дословно. Зарплатных правил v2 (диапазон по
верхней границе, уточнять голое «260», gross не сравнивать) в v3 НЕТ: они противоречили Д8/Д11/Д13, а
считает теперь код.

- **нет сигнала `contact_source`** — 21 код вместо 22;
- **готовность к формату — по КОНКРЕТНЫМ форматам:** `facts.formats_ready = [{format, ready}]` вместо
  одного `format_ready: yes|no`. «Подходит хотя бы один» — вывод кода по `allowed_formats`;
- **новое поле STATE `format_asked`** (пишет код): формат, о котором спросили прошлым ходом. По нему
  Наблюдатель относит короткое «да»/«нет» к конкретному формату, а не вычитывает это из прозы
  `last_asked`. Без него мультиформат держался бы на догадке модели.

Вилки в контексте больше нет и здесь: блок «Зарплатная вилка … (НЕ РАСКРЫВАТЬ!)» из контекста убран
(П4). Тело — 24,7 тыс. символов против 41,8 тыс. у v2.

### 5.2. Что в `domain/screening_split_hh/policy/`

Порт tg-ядра. Канало-независимое импортируется из `screening_split/policy/` (гарды G0–G7, гейты
зарплаты, класс `Budget`, таблица приоритета терминальных сигналов, `Reason`, `TurnPlan`,
`_resolve_salary`, эскалация переспросов и вводная перед доп-вопросами). Своё — шесть модулей:

| модуль | канальная дельта |
|---|---|
| `observation.py` | нет `contact_source`; `formats_ready` → `{формат: yes\|no}` |
| `formats.py` | мультиформат чистыми функциями: «подтвердил хотя бы один», «отказался от всех», «о каком формате спрашивать следующим» |
| `budgets.py` | без `contact_source`, зато с `field_work`; пороги те же, что в tg |
| `reasons.py` | `KO_FORMAT` / `KO_LOCATION` / `KO_LOCATION_GEO` вместо `KO_FORMAT_OFFICE/_HYBRID/_NOCITY` и `KO_GEO`; без `REPLY_CONTACT_SOURCE`. Те же три инварианта при импорте |
| `rules.py` | R5 `KO_LOCATION_GEO` · **R5a `KO_LOCATION`** (отказ про МЕСТО) · R6 `KO_FORMAT` по мультиформату · R10 без ветки источника контакта |
| `core.py` | повестка из ЧЕТЫРЁХ пунктов (зарплата → формат → разъездной → доп-вопросы), выбор формата для вопроса, накопление ответов по форматам |

Четыре решения, которых в tg не было и которые поедут в eggplant вместе с ядром:

- **отказ от одного формата — не отсев.** Пока среди допустимых есть формат, о котором кандидат не
  высказался, код спрашивает про него («в офис не готов» при `[ON_SITE, HYBRID]` → вопрос про
  гибрид). `KO_FORMAT` — только когда отказ получен по ВСЕМ допустимым;
- **смена формата в вопросе не считается переспросом.** Кап тикает по паре
  (`last_asking`, `format_asked`): иначе кандидат, честно ответивший про каждый формат, сжигал бы
  бюджет собственными ответами;
- **`KO_LOCATION` против `KO_FORMAT` выбирает код** по смыслу отказа: отказ переезжать при известном
  городе, отличном от локации вакансии, → `KO_LOCATION`; отказ от самих форматов → `KO_FORMAT`.
  Радиусов («Москва + 100 км») код не знает и не выводит: в v2 их прикидывала модель, здесь нужен
  ЯВНЫЙ отказ от переезда;
- **код САМ спрашивает про переезд**, когда город известен и не совпадает с локацией: «готов ли
  работать в таком формате и готов ли переехать в этот город». Это не косметика — см. §5.3.

### 5.3. Отсев по формату и локации: правка, которая едет вместе с ядром

Ключи `KO_FORMAT_*` (tg) и `KO_LOCATION` (hh) были достижимы только на бумаге: правило требовало
отказа от переезда, а код про переезд не спрашивал вовсе. Кандидат из другого города получал
`STOP_PERSISTENT` вместо объяснения. Разбор и доказательства — [review_20260831.md](review_20260831.md);
здесь только состав, потому что в eggplant это приедет вместе с ядром.

| часть правки | где |
|---|---|
| `same_city` + `relocation_pointless` | `policy/geo.py` (общий для обоих каналов) |
| вопрос про переезд как третья форма вопроса о формате | `policy/core.py::_ask_slot` |
| R6: «переезд не спасает» вместо «не готов переехать» + второй вход (отказ ПРО МЕСТО без слов про формат) | `policy/rules.py`; в hh второй вход — отдельное правило R5a → `KO_LOCATION` |
| `relocation_ready` как поле состояния | `state.py` (`init_state`, `apply_updates` — немонотонно), `policy/core.py::_updates_from_observation` |
| дефолт полю у старых диалогов | `policy/migration.py`; в eggplant это тот же JSONB-дефолт, Alembic не нужен |

**Правка целиком в коде, промпт менять не надо.** Выпущенный v3 уже описывает `relocation_ready` как
«явно сказал, готов ли переехать в город вакансии», и прямой ответ на прямой вопрос под это описание
попадает. Абзац «мы иногда спрашиваем одним сообщением» был написан и снят: он описывает НАШЕ
поведение, а не факт, и стоил бы переиздания уже выпущенного v3.

В `tgApi` правка лежит коммитом `9c2faea` (не запушен) — состояние ветки см. [../repos.md](../repos.md).

### 5.4. Ленивая миграция: что именно понадобится в eggplant

В харнессе миграции нет и не нужно: стор in-memory, диалог живёт один прогон. **Для `eggplant-api`
это НЕ так** — прод работает, и диалоги, начатые старым движком, придут в новое ядро:

- их `context` содержит строку «Зарплатная вилка: … (НЕ РАСКРЫВАТЬ!)»
  (`app/assistants/screening/context.py`) — ровно тот же формат, что в tg. Значит нужны обе операции
  tg-миграции: **разобрать числа в типизированную вилку и только потом вырезать строку**. Порядок
  обязателен, и цена ошибки скрытая: без вилки `compare_with_band` всегда возвращает «проходит», то
  есть зарплатный отсев отключается ТИХО;
- их `state` — это старый `init_state`: нет ключей `formats`, `format_asked`, `relocation_ready`,
  `questions_intro_sent`, `last_sent`; есть свой `greeted`. Это JSONB, поэтому добить дефолтами можно
  КОДОМ при загрузке — Alembic для этого не нужен;
- `last_asking` надо обнулить: у поля сменился автор (писала модель, станет писать код).

**Alembic-ревизия нужна ровно для одного** — если типизированную вилку `{min, max, currency}` решим
хранить колонкой. Собирать её на лету из `hh_vacancy_data["salary"]` — ревизии не требует, но тогда
`currency` надо читать именно там (это и есть незакрытый P11). Решение открыто, см. п. 4.

**Порядок между репозиториями тот же, что на tg: сначала код в master, потом релиз промпта.** Код
терпит отсутствие поля, промпт без кода отдавал бы наблюдение в пустоту.

## 6. Чем гонять

Из штаба (`ai-agents`) — только тесты промптов:

```bash
# новое ядро (Наблюдатель + policy + гарды) — промпт v3 обязателен
python -m qa_harness.runners.screening_split --channel hh --engine policy --analyzer-version v3 --prompts-path ../prompts

# бесплатный детерминированный гейт: мультиформат, ключи отсева, бюджеты канала (27 проверок)
python -m qa_harness.runners.screening_split --channel hh --offline --sample 1

# тест нормальных диалогов канала: 5 траекторий целиком (A — лестница мультиформата, E — локация)
python -m qa_harness.runners.screening_dialogue --channel hh --offline               # бесплатно, B пропускается
python -m qa_harness.runners.screening_dialogue --channel hh --prompts-path ../prompts

# действующий движок (контракт Decision) — как и раньше, по умолчанию
python -m qa_harness.runners.screening_split --channel hh --prompts-path ../prompts
```

Раннер общий, канал переключает движок (`domain/screening_split_hh/`), компоненты промптов и фикстуры
(`tests/fixtures/screening_split_hh/`); `--engine` переключает старое ядро на новое внутри канала.
Без `--analyzer-version v3` на `--engine policy` уйдёт версия из `pointer.yaml` (сейчас v1), а она
возвращает `Decision` — каждый ход свалится в фолбэк.

**Что проверено и чем.** Офлайн-гейт (27 проверок, без сети и токенов), тест диалогов канала (4 из 5
кейсов офлайн, B — только онлайн) и прогон тракта на заглушках: контекст без вилки, проекция состояния
без служебных полей, подмена выдуманной ссылки гардом G7 на ту, что лежит в «Описание вакансии».
**Живого прогона на hh-канале с новым ядром не было** — как и в tg, качество промпта офлайн-гейтом не
проверяется: наблюдение там скриптовано нами.

`pytest`, `alembic`, `docker compose` для `eggplant-api` запускаются **из его репозитория**: у него
Python 3.14 + Postgres + Celery, у харнесса venv 3.12.

## 7. Правила, о которых легко забыть

- В продуктовом репо — сначала **ветка** от свежего `master`; коммит только по явной просьбе;
  `git push` и `gh pr create` запрещены правами — пушит человек.
