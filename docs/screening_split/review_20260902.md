| что | было | стало |
|---|---|---|

## 2. Сценарий 60 (tg): лимит пауз «3 за жизнь»

Политика: `pause` — событийный счётчик с `fires_on_nth=3`, `resume` его **не сбрасывает**. Ход resume
продолжает повестку обычным порядком. Сценария на это не было (`STOP_PAUSE` держал только
`screening_counters`). Заведён tg №60: пауза → resume → пауза → пауза.

Нюанс, найденный на заглушках до онлайна: наивная цепочка из четырёх ходов на фокусе `salary` **не
доходит** до `STOP_PAUSE` — каждый ход без ответа на вопрос о зарплате тикает `salary_reasks`, и на
третьем срабатывает R8 `STOP_SALARY_DEMAND` раньше третьей паузы (R7 стоит выше R8, но событие паузы
на том ходе только второе). Поэтому в рецепте кандидат на ходе resume закрывает приоритеты — фокус
уезжает, счётчик переспросов не копится. Живой прогон (`20260902_202633`):

| ход | реплика | правило | исход | `counters.pause` |
|---|---|---|---|---|
| 1 | «сейчас не могу говорить, давайте позже» | R10 | `ASK_SALARY` + convey паузы | 1 |
| 2 | «готов продолжить: 240000 на руки, живу в Москве» | R11 | `ASK_Q1` (модель закрыла зарплату, город и формат одним ходом) | 1 |
| 3 | «опять отвлекают, давайте позже» | R10 | `HOLD_PAUSE` — без вопроса | 2 |
| 4 | «всё ещё занят, напишите позже» | R7 | `STOP_PAUSE`, «Прошу прощения за беспокойство.», `end` | 3 |

Сценарии про паузы 34, 35, 37, 38 прогнаны тем же прогоном — 4/4, resume продолжает с того же шага.
Итог 5/5.

## 5. Паритет ядра с `eggplant-api`

Источник: `../eggplant-api`, ветка `feat/screening-policy-engine`, коммит `69ec645`; сравнение по коду
(докстринги и комментарии вырезаны AST-ом, тела нормализованы `ast.unparse`).

**Совпадает:** `rules`, `budgets`, `observation`, `reasons`, `formats`, `geo`, `gates`, `guards` (разница —
аннотации типов и `str(currency)` в `gates`); `salary.py`/`salary_rules.py`; Наблюдатель (3 попытки, формат
входа, мягкая валидация); формат хода Интервьюера; оркестрация `run_turn` ≡ `PolicyEngine.add_message_and_run`
(observe → decide → speak → приветствие один раз на `ask` → `last_sent` → save, гарды с канонической ссылкой
из описания, пустой ответ → `REPLY_FALLBACK`); версии промптов (`screening_analyzer_hh` v3, Интервьюер по
`pointer` = v1) — ровно то, что гонялось.

**Расходится / тест не видит:**

| где | eggplant | харнесс | следствие |
|---|---|---|---|
| флаг движка | `SCREENING_ENGINE` по умолчанию `legacy` (`config.py:51`) → без переменной работает монолит `screening_assistant_hh` | тестирует split безусловно | результаты прогона относятся к eggplant **только при `SCREENING_ENGINE=split`** |
| миграция старых диалогов | `policy/migration.py` + `upgrade()` в `run_turn`, `band_unparsed` → `REPLY_FALLBACK` без завершения | миграции в hh-ядре нет | покрыто только pytest самого eggplant |
| вход контекста | контекст хранится строкой, факты на каждом ходе **парсятся обратно** по меткам (`facts_from_context`); гео — маркеры только в `location + description` | словарь вакансии; `has_geo_restriction` принимает и явное поле `geo_restriction` | hh-фикстуры поля не используют — для прогона эквивалентно; появись оно, тест доказывал бы то, чего eggplant не умеет |
| реальные данные HH | `description` — HTML из API, `location` = `address.city` (бывает пустым), форматы через `normalize_work_formats` (`process_screening.py:196-205`) | фикстуры — чистый текст, город всегда есть | качество Наблюдателя на HTML и поведение при пустой локации не измерены ни одним сценарием |
| `state.apply_updates` | принимает `relocation_check: pending` как update | ставит поле напрямую | эквивалентно |
| слой B | нет | `InterviewerJudge`, `leak_scan`, `injection_scan`, инварианты | провалы слоя B — про тест, не про продукт |

Вывод: **ядро и оркестрация split-движка в eggplant и в тесте — одно и то же**; расходятся обвязка
(миграция, парсинг контекста) и реальный вход HH.
