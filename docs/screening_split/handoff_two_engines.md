# Два движка split-скрининга: действующий и новый — контекст для анализа ошибок

Документ самодостаточный: его можно вставить в чистый чат целиком. Задача, под которую он написан —
**взять конкретную ошибку, случившуюся на действующем движке, и понять, повторится ли она на новом.**

Состояние на 2026-08-29.

> **Читать первым.** Новый движок написан и проверен ОФЛАЙН и на детерминированном наборе сценариев.
> **В проде он не работал ни разу.** Что именно проверено, а что нет — §8. Не принимайте «в новом
> движке этого не будет» за наблюдение: почти всегда это вывод из устройства кода, а не из прогона.

## 1. Где что лежит

Три репозитория. Знание о продуктовых репо хранится в `ai-agents` (он же штаб); ссылки идут только в
одну сторону — отсюда туда.

| репозиторий | роль |
|---|---|
| `tgApi` | прод, telegram. Движок и ассистенты |
| `eggplant-api` | прод, hh. Свой порт того же движка, **новая архитектура туда НЕ переносилась** |
| `prompts` | тела промптов, ставятся в прод пакетом из GHCR-образа |
| `ai-agents` | QA-стенд: порт движка + раннеры + вся документация |

> `tgApi/app/common/screening/ScreeningSplitEngine.py` на месте. Различить их можно только по ветке:
>
> ```

> **В харнессе оба движка лежат рядом и никуда не делись:** старый — `engine.py`, новый —

## 2. Что общего у обоих движков

Не меняется ничего из перечисленного — если ошибка коренится здесь, новый движок её НЕ исправит.

- **Три участника:** Аналитик/Наблюдатель (LLM, gpt-4.1, `temperature 0`, stateless) · Интервьюер
  (LLM, gpt-4.1-mini, о вакансии не знает; в НОВОМ движке stateless, в старом — stateful через
  OpenAI-conversation) · код-оркестратор.
- **Интервьюер не видит контекст вакансии** — только персона и имена. Любой факт должен быть вложен
  в инструкцию.
- **Завершение диалога — всегда за кодом.**
- **Движок событийный:** ход запускается входящим сообщением, при сбое отправки ход теряется.
- **Модуль зарплаты не менялся:** `salary.py`, `salary_rules.py` — те же четыре гейта годности claim,
  та же арифметика (масштаб → курс → период → gross→net), то же правило сравнения: отказ только
  если НИЖНЯЯ граница ожиданий выше нашего максимума.
- **Реестр скриптов по смыслу тот же** — тексты и терминальность совпадают, кроме двух правок (§6.7).
- **Пороги счётчиков по значениям те же:** gibberish/bot_check на 2-м, demand/contact_source/pause на
  3-м, лимит переспросов на 3-м, `no_progress` на 4-м ходу без прогресса.

## 3. ДЕЙСТВУЮЩИЙ движок: как устроен ход

### 3.1. Контракт `Decision` — 7 полей

Схема: `prompts/screening_analyzer/v2/config.yaml`, `strict: true`.

| поле | значение |
|---|---|
| `next_action` | `ask` \| `script` |
| `script_key` | ключ скрипта при `script`, иначе `null` |
| `instruction` | директива Интервьюеру при `ask`. Максимум 2 задаваемых вопроса |
| `updates` | `[{key, value}]` — что изменилось на этом ходе |
| `event` | `bot_check` \| `gibberish` \| `salary_info` \| `demand` \| `contact_source` \| `pause` \| `null` |
| `asking` | `salary` \| `format` \| `q1`/`q2`/… \| `null` — по нему код считает переспросы |
| `salary_claim` | объект из 9 полей либо `null` |

**Ключевое:** первые четыре поля — это уже ИСХОД хода. Модель выбирает действие.

Валидация — [decision.py](../../src/qa_harness/domain/screening_split/decision.py): 6 обязательных
полей (`salary_claim` в список не входит), `next_action` в перечислении, при `script` ключ известен
реестру, при `ask` непустая `instruction`. Невалидно → до 3 попыток → `AssistantError` →
`REPLY_FALLBACK`.

### 3.2. Порядок одного хода

Файл: [engine.py](../../src/qa_harness/domain/screening_split/engine.py), метод `add_message_and_run`.

```
0.  store.load(cid)                      нет записи → REPLY_FALLBACK · finished → молчим
1.  progress_before = progress_signature(state)
2.  analyzer.run(context, state, message) → Decision            ← ВЫЗОВ LLM #1
3.  ЗАРПЛАТА ч.1: claim → claim_status → normalize              :229-238
4.  apply_updates(state, _gate_salary_update(updates, status))  БЕЗ event   :245
5.  ПЕРЕРЕШИВАНИЕ #1: claim непригоден И решение исходило из «деньги закрыты»
       analyzer.run(..., note=_SALARY_REWIND_NOTE)              ← ВЫЗОВ LLM #2   :257-270
6.  ЗАРПЛАТА ч.2: compare_with_band → ko | fits                 :281-320
       ko  + вердикт вправе перебить → KO_SALARY, _forced=True
       fits + модель дала денежное завершение → _release_money_stop
       fits + модель всё ещё спрашивает про деньги → ПЕРЕРЕШИВАНИЕ #2  ← ВЫЗОВ LLM   :304-320
7.  ИНКРЕМЕНТ event (первого решения)                            :325-326
8.  АУДИТ: store.log_salary_claim                                :328-344
9.  ПОРОГИ СОБЫТИЙ (_EVENT_STOP) → форс STOP_*, _forced=True     :350-354
10. REASK-CAP по decision.asking → форс STOP_* / refused         :364-400
       исчерпан доп-вопрос → refused + analyzer.run(...)         ← ВЫЗОВ LLM
11. NO_PROGRESS-CAP (4 хода без прогресса)                       :404-410
12. РЕНДЕР: script → текст из реестра · ask → interviewer.run()  ← ВЫЗОВ LLM
13. store.save_state(...)
```

**Вызовов LLM за ход: 1–3.**

### 3.3. Кто что решает

| решение | кто | где |
|---|---|---|
| какой триггер сработал и какой из них главный | **модель** | промпт `v2:137` — таблица приоритета из 19 позиций |
| какой скрипт отправить | **модель** | `Decision.script_key` |
| какой вопрос задать следующим | **модель** | `Decision.instruction` + `asking` |
| текст инструкции целиком, включая факты и эмпатическую рамку | **модель** | `Decision.instruction` |
| закрыть ли пункт зарплаты | код (гейтом), но ключ ставит модель | `_gate_salary_update` |
| отсев по вилке | **код** | `compare_with_band` |
| пороги счётчиков и лимит переспросов | **код** | `_EVENT_STOP`, reask-блок |
| завершение диалога | **код** по ключу модели | `scripts.is_terminal` — по префиксу имени |

### 3.4. Девять конструкций, которые компенсируют порядок

Все они существуют потому, что модель приняла решение раньше, чем код успел посчитать:

`_release_money_stop` (:101) · `_assumes_salary_closed` (:116) · `_gate_salary_update` (:135) ·
`_SALARY_REWIND_NOTE` (:64) · флаг `_forced` (:278, :289, :350, :364) · отложенный инкремент `event`
(:322) · перерешивание по непригодному claim (:257) · перерешивание `closed_reask_dropped` (:304) ·
перерешивание по исчерпанному доп-вопросу (:385).

## 4. НОВЫЙ движок: как устроен ход

### 4.1. Контракт `Observation` — 7 полей

Схема: `prompts/screening_analyzer/v3/config.yaml`. Валидация —
[policy/observation.py](../../src/qa_harness/domain/screening_split/policy/observation.py).

| поле | значение |
|---|---|
| `signals` | до 3 сигналов `{code, quote}` из закрытого списка (22 кода). **Цитата обязательна** |
| `focus_answered` | `substantive` \| `deflection` \| `refusal` \| `none` — про НАШ прошлый вопрос |
| `persistent` | bool — повторяет то же требование с маркером нажима |
| `facts` | `candidate_city`, `format_ready`, `relocation_ready`, `geo_blocked` |
| `answers` | `[{key, substantive}]` — на какие доп-вопросы ответил |
| `salary_claim` | 9 полей, **1:1 как в v2** |
| `reply_material` | `[{kind, text}]` — куски ответа ПО СУЩЕСТВУ вакансии |

**Полей `next_action`, `script_key`, `instruction`, `asking`, `event` в контракте НЕТ.** Модель не
может вернуть исход — его негде выразить.

Два правила, на которых держится конструкция:

- **сигнал без цитаты, найденной в реплике, отбрасывается** — цена выдуманного `not_interested` это
  необратимо закрытый диалог;
- **валидация мягкая:** жёстко обязательны только `signals` и `focus_answered`, остальное чинится
  дефолтом. Ошибка в одном блоке не стоит трёх перегенераций хода.

### 4.2. Порядок одного хода

Файл: [policy/core.py](../../src/qa_harness/domain/screening_split/policy/core.py), функция `decide`
— **чистая функция, ни сети, ни стора, ни вызовов LLM**.

```
0.  канал: store.load → ленивая миграция документа (policy/migration.py)
1.  observer.run(context, state_for_prompt(state), message) → Observation   ← ВЫЗОВ LLM #1 (единственный)
2.  ЗАРПЛАТА целиком: claim_status → normalize → compare_with_band
       → односторонние гейты понижения (policy/gates.py)
3.  ФАКТЫ и ОТВЕТЫ → состояние, монотонно
4.  СЧЁТЧИКИ: ровно один за ход
5.  ФОКУС и бюджет переспросов
6.  ТАБЛИЦА ПРАВИЛ R1–R11 — первое сработавшее выигрывает
7.  СБОРКА ИНСТРУКЦИИ: [ответ модели] + [реакция кода] + [вопрос кода по шаблону]
8.  РЕЧЬ: скрипт из реестра причин · либо Интервьюер → ШЛЮЗ ГАРДОВ    ← ВЫЗОВ LLM #2 (0 или 1)
9.  store.save_state
```

**Вызовов LLM за ход: 0 (диалог закрыт) · 1 (ход-скрипт) · 2 (ход с вопросом). Третьего не бывает
структурно — второго вызова Наблюдателя в движке нет.**

### 4.3. Таблица правил

[policy/rules.py](../../src/qa_harness/domain/screening_split/policy/rules.py). Код идёт сверху вниз,
берёт первое сработавшее.

| # | когда | исход |
|---|---|---|
| R1 | диалог закрыт | молчим |
| R2 | наблюдения нет (сбой) | `REPLY_FALLBACK`, диалог продолжается |
| R3 | пришёл терминальный сигнал | верхний по приоритету `STOP_*` |
| R3a | …но кандидат ответил по сути | «нет опыта» не исполняется |
| R3b | …но рядом стоит вопрос про вакансию | «не интересно» и «критика» не исполняются |
| R4 | ожидания выше максимума вилки | `KO_SALARY` |
| R5 | гео-ограничение не выполнено | `KO_GEO` |
| R6 | не готов к формату и переезд не спасает — ЛИБО отказ от переезда из другого города (про формат молчит) | ключ выбирает код по формату вакансии |
| R7 | исчерпан порог счётчика | `STOP_*` по строке бюджета |
| R8 | исчерпан лимит переспросов | стоп либо «пометить refused и идти дальше» |
| R9 | всё собрано | `FINISH` |
| R9a | 4 хода без прогресса | `FINISH` либо `STOP_PERSISTENT` |
| R10 | нетерминальный сигнал | скрипт либо ответ + следующий вопрос |
| R11 | по умолчанию | вопрос текущего фокуса |

Порядок несёт прежние решения буквально: **R3 > R4** (неденежное терминальное сильнее отсева по
деньгам) · **R4 > R7** (зарплатный вердикт выше порогов) · **R4 > R9** (`ko` перебивает `FINISH`).

### 4.4. Кто что решает теперь

| решение | кто | изменение |
|---|---|---|
| какие сигналы прозвучали | **модель** | не изменилось, но теперь возвращает ВСЕ (до 3), а не один |
| **какой из сигналов исполнить** | **код** | ⬅ было у модели |
| **какой скрипт отправить** | **код** | ⬅ было у модели |
| **какой вопрос задать следующим** | **код** | ⬅ было у модели |
| **текст вопроса** | **код**, по шаблону со вставленными значениями | ⬅ было у модели |
| ответ по существу вакансии | **модель** | не изменилось — контекст видит только она |
| закрыть ли пункт зарплаты | **код** | ключа `salary` в контракте больше нет |
| отсев по вилке, пороги, лимиты | **код** | не изменилось |
| **завершение** | **код**, терминальность из реестра | ⬅ было по префиксу имени ключа |
| **форма сообщения** | модель + **детерминированные гарды** | ⬅ гардов не было |

### 4.5. Чего в новом движке нет

Все девять конструкций из §3.4 отсутствуют, и не «убраны», а **невыразимы**: к моменту выбора
действия всё уже посчитано, поэтому решения, с которым код может не согласиться, не существует.

## 6. Известные классы ошибок действующего движка — и что с ними в новом

**Это главный раздел для вашей задачи.** Столбец «механизм» отвечает на вопрос «почему исправится».

| # | ошибка на действующем движке | причина | в новом движке | механизм |
|---|---|---|---|---|
| 1 | **Выдуманная ссылка на вакансию.** Интервьюер контекста не видит и сочиняет URL, когда кандидат спрашивает про вакансию. ### 6.1. Классы ошибок, которые новый движок НЕ исправляет

Если ваша ошибка попадает сюда — она повторится.

- **Модель не распознала сигнал или распознала не тот.** Весь слой распознавания остался за LLM.
  Код может только не исполнить услышанное, но не может услышать за неё.
- **Модель неверно заполнила `salary_claim`** (кроме `scale`/`currency`, которые прикрыты гейтами).
- **Модель ошиблась в `focus_answered`** — новое поле, своих ошибок ещё не показало.
- **Потеря хода при сбое отправки** — движок событийный, согласования отправки нет ни там, ни там.
- **Всё, что делает Интервьюер** — он не изменился; изменилось только то, что часть инструкции ему
  теперь пишет код, и что его текст проходит через гарды.

### 6.2. Новые классы ошибок, которых на действующем движке быть не могло

- **Гард испортил сообщение.** Защитные гарды меняют текст. Теневой замер по 1192 записанным
  сообщениям: 2 защитных срабатывания, ложных нет — но это замер, а не гарантия.
- **Наблюдения верные, комбинация не предусмотрена.** Часть работы, которую промпт делал прозой,
  переехала в предикаты правил. Незакрытая комбинация даёт неверный маршрут.
- **Две директивы кода противоречат друг другу.** Уже случалось на прогоне: реакция «объясни, почему
  нужен ответ в чате» склеилась с шаблоном переспроса «ничего не объясняй, только вопрос».
- **Отрицательная инструкция исполняется наоборот.** Уже случалось: «не спрашивай, когда именно
  удобно» → модель спросила именно об этом.
- **Ошибка в порядке вычислений внутри ядра.** Уже случалась: стоп-кран `no_progress` проверялся по
  значению ДО хода, и ход, где кандидат наконец назвал город и сумму, добивал счётчик вместо
  обнуления.

## 8. Что проверено, а что нет

### Проверено

- **Переигрывание записанных трасс:** 523 хода из реальных прогонов пропущены через новое ядро —
  **0 расхождений** по исходу, завершению и состоянию. Проверяет арифметику и порядок КОДА; качество
  наблюдения и правила R3a/R3b не проверяет, потому что старый `Decision` отдаёт один ВЫБРАННЫЙ
  сигнал, а не все увиденные.
- **Офлайн-гейт:** 50/50 зарплатного контракта + 18/18 ленивой миграции, без сети и токенов.
- **Живой прогон scripted** по всем 77 сценариям — лучший результат 75/77 против 76/77 у
  действующего стека. **Паритет не подтверждён**: замер требует по три прогона на стек, они не
  делались.
- **Теневой замер гардов:** 2340 записанных сообщений, 21 защитное срабатывание, ложных нет.
- **Сверка контракта промпта с контрактом кода:** словарь сигналов, значения `focus_answered`,
  отсутствие полей решения.

### Не проверено

- **Прогон `--input-mode generated` не делался ни разу.** Робастность на вариативных формулировках
  неизвестна.
- **Порт в tgApi ни разу не запускался** в своей среде: только `py_compile` и статическая сверка
  47 импортов.
- **hh-контур не трогали вообще** — `eggplant-api` остаётся на прежней архитектуре, а
  `screening_analyzer_hh` содержит правила, прямо противоречащие принятым для tg.
- **Шум гейта:** два прогона действующего стека на неизменной версии дали 76 и 74, и ни один
  сценарий не упал дважды. То есть разница в 1–2 сценария между стеками сама по себе ничего не
  значит.

## 9. Как пользоваться этим документом

Чтобы ответить «повторится ли ошибка X»:

1. **Определите, где принималось решение, которое пошло не так** — по таблице §3.3. Если строка
   помечена «модель», смотрите §4.4: перешло ли это решение к коду.
2. **Найдите ошибку в таблице §6.** Если её там нет — проверьте §6.1: не относится ли она к слою
   распознавания, который не менялся.
3. **Проверьте §6.2** — не создаёт ли новый движок для этого случая свою ошибку взамен.
4. **Сверьтесь с §8** — есть ли под ваш вывод прогон, или это рассуждение из устройства кода.

[decisions_rearchitecture.md](decisions_rearchitecture.md) — журнал решений Р1–Р14 с мотивировками,
[mechanics_decision.html](mechanics_decision.html) — механика действующего движка со схемами,
